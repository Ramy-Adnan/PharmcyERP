# استلام فواتير المذاخر من الصور والوحدات المرنة

بعد تحديث المشروع: أغلق التطبيق وVisual Studio، افتح Visual Studio ونفّذ **Git → Pull → Rebuild Solution → F5**. لا تحتاج Clone جديداً ولا قاعدة جديدة. الترحيل `AddFlexibleUnitsAndInvoiceImageImports` يضيف تعريفات الوحدات وسجل الاستيراد والبونص إلى قاعدة الاتصال الحالية، ويترك الأرصدة والفواتير السابقة بوحداتها الأصلية.

## تفعيل قراءة الصور على Windows

القراءة تستخدم OpenAI API عبر الإنترنت، وتحتاج [حساب API بمفتاح](https://platform.openai.com/api-keys) ورصيد؛ اشتراك ChatGPT وحده لا يفعّلها. في Windows افتح **Edit environment variables for your account → User variables → New**:

- الاسم: `PHARMACYERP_VISION_API_KEY`.
- القيمة: مفتاح API الخاص بك.

أعد تشغيل Visual Studio والتطبيق بعد إضافة المتغير. لا ترسل المفتاح في المحادثة ولا تضعه في Git أو appsettings. يستخدم التطبيق افتراضياً `gpt-4.1-mini`؛ يمكن تعيين `PHARMACYERP_VISION_MODEL` إلى نموذج آخر يدعم الصور وStructured Outputs. المتغير البديل `OPENAI_API_KEY` مقبول أيضاً.

عند الضغط على اختيار صورة وتحليلها تُرسل تلك الصورة إلى OpenAI. الصورة ليست محفوظة في قاعدة المشروع؛ يُحفظ رقم الفاتورة وبصمة الصورة والمراجعة المعتمدة. المعاينة تستخدم الصورة في الذاكرة. عند غياب المفتاح أو الإنترنت تظهر رسالة، ويظل الإدخال اليدوي متاحاً دون اعتماد مخزون.

## الاستلام خطوة بخطوة

1. افتح **مسار المشتريات** واختر المذخر المسجل كمورد.
2. انتقل إلى **البضاعة المستلمة** وحدد المخزن. ابدأ بسند جديد فارغ، ثم اضغط **استيراد فاتورة من صورة**.
3. اختر صورة واضحة لفاتورة واحدة بصيغة JPG/PNG/WEBP لا تتجاوز 8MB. الصور الثلاث ذات أرقام فواتير مختلفة تُستورد كعمليات مستقلة. افحص اسم المورد المقروء وتأكد أنه المورد المختار. الأرقام المالية بالدينار العراقي؛ لا تعتمد فاتورة بعملة أخرى دون تحويل مقصود للأسعار.
4. راجع رقم الفاتورة والتاريخ وإجمالي الفاتورة نفسه؛ **الرصيد بعد الفاتورة ليس إجماليها**. يظهر مجموع الأسطر للمقارنة، ولا يقبل الحفظ عند اختلافه عن الإجمالي الذي راجعته.
5. حدّد كل سطر لفتح تفاصيله. المطابقة المؤكدة بالاسم الكامل أو الباركود أو تسمية المذخر المحفوظة تقترح البطاقة الموجودة. الأسماء المشابهة تظهر كمرشحين فقط؛ اختر البطاقة الصحيحة أو «بطاقة علاج جديدة». راجع التركيز؛ الشركة المصنّعة اختيارية.
6. للعلاج الجديد اختر التصنيف والشكل الدوائي ووحدة المخزون الصغيرة، وراجع متطلبات الوصفة والرقابة. لا نستنتج هذه القيود من اسم الفاتورة. يمكنك إضافة وحدة مخزون مثل «حبة» أو «أمبولة» بالزر أعلى الشاشة إذا كانت لديك صلاحية إدارة الوحدات.
7. حدّد **اسم وحدة الاستلام** و**عدد أجزاء وحدة المخزون داخلها**. راجع الكمية المدفوعة والبونص وسعر شراء الوحدة وسعر بيعها ورقم الدفعة والصلاحية. سعر البيع المقترح يزيد 20% لباي هاند و25% للباقي، ويمكن تعديله. تغيير بيانات السطر يزيل علامة المراجعة.
8. إذا كانت الدفعة أو الصلاحية غير ظاهرة فلن يُخترع رقم أو تاريخ؛ افحص العبوة وأكمل الحقل. استخدم **عرض الصورة الأصلية** للتكبير والمقارنة. يعرض الجدول مبلغ السطر المطبوع ومبلغه المحسوب؛ صحّح أخطاء القراءة حتى لو تطابق مجموع الفاتورة.
9. ضع علامة **راجعت** لكل سطر، ثم **حفظ المراجعة ومتابعة الاستلام**. تُنشأ بطاقات الأصناف الجديدة وتعريفات التعبئة المطلوبة ومسودة سند استلام، وتُحفظ المطابقة لتسمية هذا المذخر. الصنف الموجود يحصل على دفعة جديدة عند اعتماد الاستلام.
10. أكمل الخطوة التالية في مسار المشتريات لاعتماد المخزون، ثم راجع فاتورة المورد واحفظها، ثم سجّل ما دفعته. عدم الدفع أو دفع جزء يبقي المبلغ المتبقي مستحقاً للمورد.

منع التكرار يعتمد على طلب الحفظ وبصمة الصورة والمورد/رقم الفاتورة/السنة. إعادة الصورة أو تصوير الفاتورة نفسها مجدداً يفتح السند السابق بدلاً من مضاعفة الأصناف أو المخزون. سند ملغى أو محذوف يحتاج مراجعة السجل؛ لا يعاد إدخاله تلقائياً. حفظ المراجعة في SQL Server يتم داخل معاملة واحدة، فلا تُترك بطاقات أو مسودة جزئية عند فشل خطوة.

## الحبة والشريط والعلبة ليست عدداً ثابتاً

مثال الصورة: `Paracetamol 1g 20 Tab`، سعر وحدة الفاتورة 3,900:

- **إذا كان المكتوب 20 حبة داخل العلبة**: شراء الحبة = 3,900 ÷ 20 = **195**؛ بيعها بزيادة 25% = **243.75**، وبزيادة 20% = **234**.
- إذا أكدت أن الشريط يحتوي 10 حبات، عرّف وحدة إضافية **شريط = 10 حبات**. شراء الشريط = **1,950**، وبيعه بزيادة 25% = **2,437.50**. العلبة = 20 حبة وسعر بيعها **4,875**.
- إذا كانت العبوة تحتوي 20 شريطاً فعلاً، اختر وحدة المخزون «شريط» وعدد الأجزاء 20؛ عندها يكون 195 للشريط. لا نستنتج ذلك من كلمة Tab.

من **بطاقة الصنف → وحدات بيع واستلام إضافية** تستطيع تعريف شريط/باكيت/كارتون أو أي اسم آخر بمعامل مستقل. لا يوجد حد ثابت خمسة أشرطة، ولا تُحسب mg أو mL كعدد أجزاء قابلة للبيع.

في POS ابحث أو امسح الباركود، ثم اختر الوحدة من السلة. يتغير السعر والرصيد القابل للبيع، وتظل الأسعار قابلة للتعديل. يمكنك تعيين باركود مستقل لكل وحدة؛ مسح باركود الشريط يضيف الشريط، وتكراره يزيد عدده. لبيع أكثر من وحدة من الصنف نفسه استخدم **إضافة بوحدة أخرى**؛ يمر الزر على الوحدات المتاحة. مجموع الأسطر يخصم أجزاءها من رصيد مشترك، والوصل والمرتجع يحتفظان بوحدة البيع الأصلية.

## تعبئة مختلفة في دفعة لاحقة

إذا كانت البطاقة بوحدة مخزون «حبة» وعلبة أصلية 20، واستلمت تعبئة 30 حبة: أبقِ وحدة المخزون نفسها وحدّد وحدة الاستلام الجديدة ومعاملها 30. تُضاف وحدة تعبئة مستقلة، ولا يعاد تفسير العلب أو المبيعات القديمة. يمكن إضافة وحدات جديدة دائماً؛ تعريف الوحدة المستخدمة لا يغيّر اسمه أو معاملها بعد وجود حركات، ويمكن إيقافها للاستخدامات الجديدة.

البطاقة القديمة التي كانت وحدة مخزونها «علبة» لا تتحول تلقائياً إلى حبات؛ ذلك يحتاج جرداً وتسوية مقصودة أو بطاقة صحيحة جديدة، كما في [دليل الوحدات](Packaging-sales-ar.md).

## البونص والسعر

فاتورة 10 علب × 3,900 مع بونص علبتين، وكل علبة 20 حبة:

- المستحق للمورد **39,000** فقط.
- المخزون **240 حبة**: (10 + 2) × 20.
- تكلفة المخزون الفعلية للحبة **162.50**: 39,000 ÷ 240، لأن تكلفة البونص موزعة على الكمية المستلمة.
- اقتراح البيع يُحسب من سعر الشراء المطبوع لوحدة الفاتورة، ثم يتقسم على الأجزاء؛ يبقى سعر العلبة 4,875 بزيادة 25% ما لم تعدله.

## حدود التحقق

اختبارات آلية تغطي عقد HTTP والتحليل المنظم دون مفتاح حقيقي، وتستخدم مبالغ من الصور نُقلت يدوياً للتحقق من إجماليات 418,368 و631,649 و295,539 واستبعاد البونص من المستحقات. اختبارات SQLite تتحقق من القيود والتراجع عن حفظ استيراد جزئي، واختبارات POS تتحقق من بيع الشريط والحبة والمرتجع والمخزون المشترك. نجح بناء WPF في Linux. لم يُجرّب تحليل الصور عبر API حقيقي لعدم توفر المفتاح في البيئة، ولا تشغيل الواجهة والترحيل على SQL Server أو الماسح والطابعة الفعليين؛ هذه التجارب على جهاز Windows.
