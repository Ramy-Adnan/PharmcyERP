# تجهيز نسخة الزبائن والتحزيم في Advanced Installer 19.5

يتكوّن التسليم من تطبيق منشور، ومثبت Windows، وترخيص خاص بالزبون. قاعدة بيانات الصيدلية وإعداداتها ليست ملفات تضعها داخل مثبت عام لجميع الزبائن.

## ما يُجهّز على جهاز المطوّر

- Windows ‏64-bit لبناء وتجربة المثبت باستخدام Advanced Installer 19.5.
- ‎.NET SDK لبناء المشروع. البرنامج المنشور يتضمن ‎.NET وWindows Desktop Runtime؛ أجهزة الزبائن لا تحتاج SDK أو Visual Studio أو Git.
- مفتاح إصدار تراخيص خاص بك، ونسخة احتياطية آمنة منه. يبقى المفتاح الخاص وأداة `LicenseIssuer` وسجل الزبائن على جهازك؛ يضم التطبيق مفتاح التحقق العام فقط.
- إصدار رقمي جديد لكل تسليم، مثل `1.1.0`. يستخدمه التطبيق ومثبت Windows معاً. لا تُعد استخدام رقم إصدار لملفات مختلفة.

## 1. إنشاء مفاتيح الترخيص مرة واحدة

من مجلد المشروع في PowerShell، اختر مجلداً خاصاً خارج Git وخارج مجلد النشر:

```powershell
dotnet run --project .\tools\LicenseIssuer -c Release -- keygen --private-key "C:\PharmacyERP-Vendor\private-encrypted.pem" --public-key "C:\PharmacyERP-Vendor\public.pem"
```

ستطلب الأداة عبارة سرية للمفتاح الخاص بإدخال مخفي. احتفظ بالمفتاح المشفّر وعبارته السرية في نسخ احتياطية مستقلة؛ فقدانه يمنع إصدار تراخيص متوافقة مع مفتاح التحقق الموجود في النسخ المنشورة. لا تضع العبارة في Git أو الأمر أو دليل الزبون، ولا ترفع المفتاح الخاص إلى خادم التحديثات.

استخدم المفتاح العام نفسه عند تحديث نسخ زبائنك. تغيير المفتاح العام يحتاج خطة لإعادة إصدار تراخيصهم. ملفات التوقيع القديمة المبنية على HMAC تحتاج إعادة إصدار بالشكل الجديد؛ لا تنقل سر HMAC القديم إلى أجهزة الزبائن.

## 2. نشر نسخة قابلة للتحزيم

```powershell
.\scripts\Publish-Release.ps1 -Version 1.1.0 -LicensePublicKeyPath "C:\PharmacyERP-Vendor\public.pem"
```

المخرجات:

```text
artifacts\release\1.1.0\
    app\                       ملفات التطبيق كاملة
    release-manifest.json       إصدار وSHA-256 لكل ملف
```

السكربت ينشر `Release / win-x64 / self-contained` دون دمج الملفات في EXE واحد ودون trimming. يتحقق من ملفات التطبيق وملفات لغتي OCR ومكتبات Windows الأصلية والمعمارية x64 ومفتاح التحقق المضمّن. يرفض بيانات اتصال أو مفاتيح خاصة أو ملفات تراخيص زبائن أو قواعد ونسخ احتياطية في المخرجات. يفشل إذا كان مجلد الإصدار موجوداً، ولا يحذف إصداراً سابقاً. استخدم `-OutputRoot` لاختيار مجلد نشر آخر عند الحاجة.

احتفظ بـ`release-manifest.json` مع سجلات الإصدار عندك. هو سجل للتحقق من الملفات وليس توقيعاً رقمياً موثوقاً للمثبت. لا تُعتبر سلامة الملفات وحدها إثباتاً لاجتياز اختبار التشغيل.

يمكن استخدام ملف النشر `Properties/PublishProfiles/Windows-x64.pubxml` داخل Visual Studio للمراجعة، لكن حزمة الزبائن تُنتج بالسكربت السابق لأنه يمرر المفتاح والإصدار ويفحص المخرجات.

## 3. مشروع Advanced Installer

أنشئ مشروع تثبيت للتطبيق واحفظ `.aip` في مجلد خاص بإصداراتك:

1. في **Product Details** ضع اسم المنتج والشركة وإصداراً مطابقاً للنشر، مثل `1.1.0`.
2. في **Install Parameters** اجعل الحزمة ‏64-bit، والتثبيت لكل مستخدمي الجهاز بصلاحيات المدير، إلى مجلد تحت **Program Files**.
3. في **Files and Folders → Application Folder** أضف **محتويات مجلد `app` كاملة** مع المجلدات الفرعية. لا تضف `bin\Debug` أو مجلد المشروع أو أدوات المُصدر.
4. أنشئ اختصاراً إلى `PharmacyERP.WPF.exe` في قائمة Start، واختصار سطح المكتب إن أردت.
5. في **Prerequisites** أضف Visual C++ 2015–2022 Redistributable x64 من Microsoft. لا تعتمد على وجوده في جهاز المطوّر.
6. جهّز اختياراً أو حزمة منفصلة لدور الجهاز: **جهاز رئيسي** يحتاج SQL Server محلياً، و**جهاز كاشير إضافي** يتصل بخادم موجود. لا تثبّت SQL Server على كل كاشير بلا حاجة. يمكن إضافة مثبت SQL Server Express الرسمي كمتطلب مخصص إذا لم يكن الإصدار المطلوب ضمن قائمة 19.5 الجاهزة.
7. ابنِ حزمة EXE إن أردت جمع المتطلبات مع المثبت. لتثبيت بلا إنترنت، ضمّن مثبتات المتطلبات الرسمية بعد مراجعة شروط توزيعها؛ رابط تنزيل فقط لن يكفي لجهاز غير متصل.
8. أضف مجلد بيانات مشتركاً تحت `CommonAppDataFolder\PharmacyERP` واضبط صلاحية التعديل للحسابات التي ستشغّل البرنامج. يحتاج مجلد الترخيص ومعرّف الجهاز صلاحية القراءة والكتابة عند التفعيل، ويحتاج مجلد Backups صلاحية حساب خدمة SQL Server أيضاً. لا تمنح صلاحية تعديل مجلد Program Files للمستخدم العادي.
9. جرّب تشغيل المثبت على Windows نظيف، ثم افتح البرنامج بحساب Windows عادي. لا تعتمد على تجربة تشغيله بصفة Administrator فقط.

SQL Server يحتاج مثيلاً شغالاً وصلاحيات للحساب الذي اختاره المستخدم. يختار معالج التطبيق اسم الخادم وقاعدة البيانات وطريقة المصادقة؛ لا تضع اسم جهاز المطوّر مثل `.\RAMY` في حزمة جميع الزبائن. إنشاء قاعدة وجداولها يحتاج صلاحية الإنشاء وتطبيق الترحيلات. الاتصال بقاعدة موجودة لا يعني إنشاء قاعدة بديلة لها.

إذا تنقل بيانات صيدلية قائمة، يجب أن يكون SQL Server الوجهة بنفس إصدار المصدر أو أحدث، وأن تتسع نسخته لحجم القاعدة. نسخة SQL Server Developer مخصصة للتطوير والاختبار؛ استخدم Express ضمن حدوده أو نسخة SQL Server مرخصة للاستخدام الفعلي. لعدة أجهزة، جهّز الشبكة ومشاركة النسخ الاحتياطي وصلاحيات حساب خدمة SQL Server بشكل مستقل عن اختصار التطبيق.

تعريف طابعة الفواتير وطابعة الملصقات يثبت من الشركة المصنعة. اختبر مقاس 80mm للوصل والمقاس الحقيقي للملصق، والماسح بوضع USB HID. هذه التعريفات لا توفرها حزم ‎.NET.

## 4. أول تشغيل

يمكن إعادة فتح المعالج بعد التثبيت عند تغيير الخادم باستخدام الاختصار `PharmacyERP.WPF.exe --setup`.

يتيح معالج التهيئة اختيار قاعدة جديدة أو قاعدة موجودة، واختبار الاتصال وإدخال بيانات المدير عند الحاجة. تُحفظ بيانات الاتصال المحمية بحساب Windows خارج مجلد البرنامج، ولا يتطلب الزبون أوامر PowerShell لحفظها. عند وجود متغير اتصال قديم على جهاز المطوّر، يوضح المعالج أنه يتقدم على الإعداد المحلي؛ لا تستخدم هذا المتغير كوسيلة إعداد مفروضة على الزبائن.

لا توزع كلمة مرور مدير افتراضية واحدة على جميع الصيدليات. بعد تهيئة قاعدة جديدة، افتح الإعدادات وأدخل اسم الصيدلية وشعارها وعنوانها، ثم فعّل الترخيص.

## 5. إدارة النسخ المدفوعة

يرسل الزبون البصمة من شاشة **الترخيص**. بعد تسجيل اتفاق البيع والمدفوعات عندك، أصدر ملفاً له:

```powershell
dotnet run --project .\tools\LicenseIssuer -c Release -- issue --private-key "C:\PharmacyERP-Vendor\private-encrypted.pem" --customer "صيدلية المثال" --hardware "البصمة كما أرسلها العميل" --branches 1 --users 5 --days 365 --output "C:\PharmacyERP-Vendor\Clients\example.lic" --ledger "C:\PharmacyERP-Vendor\licenses.jsonl"
```

استخدم `--perpetual` بدلاً من `--days 365` لترخيص دائم. الأداة تطلب عبارة المفتاح المخفية؛ لا ترسلها للزبون. ترسل **ملف `.lic` فقط** ليستورده من داخل التطبيق. يبقى سجل الإصدار عندك، ولا يدخل في ملف Setup.

للتجديد:

```powershell
dotnet run --project .\tools\LicenseIssuer -c Release -- renew --private-key "C:\PharmacyERP-Vendor\private-encrypted.pem" --license "C:\PharmacyERP-Vendor\Clients\example.lic" --days 365 --output "C:\PharmacyERP-Vendor\Clients\example-renewed.lic" --ledger "C:\PharmacyERP-Vendor\licenses.jsonl"
dotnet run --project .\tools\LicenseIssuer -c Release -- list --ledger "C:\PharmacyERP-Vendor\licenses.jsonl"
```

راجع التاريخ والحدود التي تعرضها الأداة قبل الإرسال. سجل التراخيص يوثق الإصدار والتجديد؛ ليس بوابة دفع ولا سجلاً محاسبياً للتحصيل. عند نقل الزبون إلى جهاز آخر، أصدر له ترخيصاً ببصمة الجهاز الجديد. لا تنقل `machine.id` كطريقة للتحايل على ربط الجهاز.

النسخة غير المفعلة أو المنتهية تبقي قراءة البيانات والنسخ والتصدير والتفعيل متاحة، وتمنع العمليات التجارية الجديدة التي تتطلب ترخيصاً. اختبر هذا السلوك في الخدمات نفسها، وليس ظهور رسالة على شاشة الترخيص فقط. التفعيل الملفي يعمل دون إنترنت، لكنه لا يحقق إلغاءً فورياً عن بُعد أو حماية منيعة من التلاعب بالجهاز؛ الإدارة المركزية الفورية تتطلب خدمة واتصالاً دورياً.

## 6. أين توجد البيانات وما الذي يُنقل

- قاعدة SQL Server تحفظ الأصناف والأرصدة والعملاء والفواتير والحركات.
- `%LOCALAPPDATA%\PharmacyERP\receipt-settings.json` يحفظ هوية الصيدلية والشعار وإعدادات الوصل.
- `%LOCALAPPDATA%\PharmacyERP\product-images` يحفظ صور المنتجات.
- إعداد الاتصال المحلي محمي بحساب Windows، ويُعاد ضبطه في الجهاز الجديد.
- إعدادات خدمات الصور المشفّرة بحساب Windows تُعاد تهيئتها على الجهاز الجديد؛ لا تنسخ ملفها على أنه إعداد صالح لكل الأجهزة.
- الترخيص ومعرّف الجهاز محليان، ويحتاج الجهاز الجديد ترخيصه الخاص.

استخدم **حزمة نقل بيانات الصيدلية** لنقل قاعدة SQL والهوية والصور معاً. ملفات `.bak` وحدها لا تشمل الملفات المحلية. تحتوي الحزمة على بيانات العميل؛ احفظها عنده أو في وجهة نسخ احتياطي يحددها، ولا تضمّنها في مثبت عام. لا يتضمن النقل المفتاح الخاص أو تراخيص الزبائن الآخرين أو أسرار خدمات AI.

حساب خدمة SQL Server هو الذي يقرأ ويكتب ملف `.bak`، وليس حساب WPF وحده. يجب أن يكون مجلد النسخ متاحاً للخدمة وللتطبيق. عند استخدام خادم بعيد، استخدم مسار مشاركة مناسباً وصلاحيات مدروسة؛ مسار `C:\...` على الكاشير لا يشير إلى القرص نفسه على الخادم.

## 7. التحديث وإلغاء التثبيت

- احتفظ بنفس **UpgradeCode** في مشروع Advanced Installer لكل إصدارات المنتج، وزد رقم الإصدار عند نشر تحديث. اضبط ترقية النسخة السابقة واختبرها قبل التسليم.
- تُحدّث ملفات التطبيق داخل Program Files. قاعدة SQL وملفات المستخدم لا تدخل في مكونات يستبدلها أو يزيلها المثبت.
- لا تضف إجراءات إزالة تحذف قاعدة العميل أو `%LOCALAPPDATA%\PharmacyERP` أو مجلد النسخ أو الترخيص. لا تجعل إعادة التثبيت تعيد تهيئة الصيدلية أو حساب المدير الموجود.
- خذ نسخة احتياطية كاملة قبل ترحيل قاعدة قائمة. نجاح تثبيت الملفات لا يثبت نجاح ترحيل SQL؛ اختبر كليهما.
- استخدم توقيع Authenticode للمثبت بمفتاح توقيع برامج مخصص إذا كان متاحاً. مفتاح توقيع التراخيص ليس شهادة توقيع Windows.
- **لا تفترض أن `/S` هو أمر Advanced Installer الصامت.** ابدأ بتشغيل تفاعلي، أو اضبط أوامر EXE/MSI المطابقة لملفك واختبرها من دليل Advanced Installer قبل تمكين تحديث صامت. لا تنشر رابط مثبت افتراضي أو غير مبني على خادم التحديث.

عميل التحديث الحالي يشغّل المثبت تفاعلياً بعد تنزيله عبر HTTPS والتحقق من SHA-256. لا يُظهر إصداراً قابلاً للتثبيت إذا كان ملف معلوماته ينقص البصمة أو الرابط الآمن. فشل التحقق يظهر كخطأ، ولا يعرض رسالة أن التطبيق محدّث. يغلق التطبيق بعد نجاح بدء المثبت فقط؛ إلغاء UAC أو فشل التنزيل يبقيه مفتوحاً. إغلاق نافذة التحديث أثناء التنزيل يلغي التنزيل قبل تشغيل أي ملف.

بعد بناء المثبت واختباره وتوقيعه إن استخدمت Authenticode، أنشئ ملف معلومات التحديث من **المثبت النهائي**؛ أي تغيير لاحق فيه يغيّر البصمة:

```powershell
$setup = "C:\Releases\PharmacyERP-1.1.0.exe"
$feed = [ordered]@{
    version = "1.1.0"
    downloadUrl = "https://updates.example.com/pharmacy/PharmacyERP-1.1.0.exe"
    sha256 = (Get-FileHash -LiteralPath $setup -Algorithm SHA256).Hash.ToLowerInvariant()
    releaseNotes = "وصف التغييرات التي جرى اختبارها"
    mandatory = $false
}
[System.IO.File]::WriteAllText("C:\Releases\latest.json", ($feed | ConvertTo-Json), (New-Object System.Text.UTF8Encoding($false)))
```

عنوان `updates.example.com` توضيحي؛ استبدله بخادم HTTPS تملكه. ارفع المثبت أولاً ثم `latest.json`، واضبط `ApplicationSettings:UpdateFeedUrl` على رابط ملفك الحقيقي في النسخة المنشورة. البصمة تتأكد من أن الملف يطابق ملف المعلومات الذي قدمه خادمك؛ لا تحل محل حماية خادم النشر أو توقيع Authenticode. لا ترفع بيانات صيدلية أو مفاتيح التوقيع إلى وجهة التحديث.

## اختبار القبول قبل بيع الإصدار

| التجربة | النتيجة المطلوبة |
|---|---|
| جهاز Windows نظيف دون SDK أو Visual Studio | المثبت يجهز المتطلبات، ويفتح المعالج ثم الدخول |
| مستخدم Windows عادي بعد التثبيت | يفتح البرنامج ويكتب إعداداته وسجلاته خارج Program Files |
| قاعدة جديدة | مدير بكلمة يختارها المستخدم، وجداول جاهزة دون بيانات صيدلية أخرى |
| اختيار قاعدة قائمة | تبقى أصنافها وأرصدتها وفواتيرها بعد الترحيل |
| اختبار OCR بالعربية والإنجليزية دون إنترنت | المحرك المحلي يعمل من الملفات المرفقة |
| ترخيص صحيح/توقيع تالف/جهاز مختلف/منتهٍ | قبول الصحيح ورفض غير الصالح مع رسالة واضحة |
| ترخيص منتهٍ أو غائب | القراءة والنسخ متاحتان؛ الكتابة التجارية مرفوضة دون تغيير المخزون |
| حدود المستخدمين والفروع والتجديد | الحدود تطبّق عند الإنشاء وإعادة التنشيط، والتجديد يحافظ على البيانات |
| SQL Server Express: نسخ ثم استعادة | لا اعتماد على ضغط غير مدعوم، والقاعدة تعود لوضع متعدد المستخدمين |
| نقل حزمة البيانات إلى جهاز بمسارات أقراص مختلفة | تُستعاد القاعدة والهوية والصور، وتُرفض الحزمة التالفة أو غير المطابقة |
| ترقية نسخة قديمة ثم إزالة وإعادة تثبيت البرنامج | البيانات والإعدادات لا تُحذف |
| بيع وطباعة فعلية وقراءة باركود | السعر والكمية والمخزون والوصل والملصق صحيحة |

تجميع WPF في Linux وفحوص الخدمات لا تعني تشغيل واجهة Windows أو SQL Server أو المثبت أو الطابعات فعلياً. سجّل نتائج اختبار Windows ورقم الإصدار الذي اختبرته قبل تسليم Setup.exe للزبائن.
