# Pharmacy ERP — Phases 0–10 (خارطة الطريق مكتملة)

## ما تم تنفيذه حتى الآن

### Phase 0 — البنية الأساسية
- بنية Clean Architecture كاملة: Domain / Application / Infrastructure / WPF
- ApplicationDbContext مع EF Core 8 + SQL Server، وInterceptor تلقائي للتدقيق (Audit) والحذف الناعم (Soft Delete)
- نظام Authentication كامل: تسجيل دخول، Lockout بعد 5 محاولات فاشلة (15 دقيقة)، تغيير كلمة المرور، سجل دخول كامل (LoginHistory)
- نظام Roles & Permissions ديناميكي (RBAC) مرتبط بكل مستخدم
- دعم Multi-Branch / Multi-Warehouse من الأساس
- AuditLog كامل لكل العمليات
- DbSeeder تلقائي ينشئ عند أول تشغيل: صلاحيات أساسية + دور "System Administrator" + فرع رئيسي + مستخدم admin
- واجهة WPF كاملة: شاشة تسجيل دخول + Shell رئيسي بعد الدخول، MVVM نظيف بدون أي Code-Behind منطقي
- Dependency Injection عبر Microsoft.Extensions.Hosting + Serilog للـ Logging

### Phase 1 — الفروع والمخازن + إدارة المستخدمين والأدوار (Security Module UI)
- **موديول الفروع والمخازن**: شاشة Master-Detail كاملة — إضافة/تعديل/تفعيل-تعطيل/حذف فرع، وإدارة مخازن كل فرع (مع قاعدة عمل: كل فرع يحتفظ بمخزن افتراضي واحد دائماً، ولا يمكن حذف الفرع الرئيسي)
- **موديول إدارة المستخدمين**: إضافة/تعديل مستخدم، تعيين الدور والفرع الافتراضي وصلاحيات وصول لفروع إضافية، تفعيل/تعطيل، إعادة تعيين كلمة المرور، إلغاء قفل الحساب (مع حماية: لا يمكن تعطيل آخر مدير نظام نشط)
- **موديول الأدوار والصلاحيات**: إضافة/تعديل/حذف الأدوار مع واجهة اختيار صلاحيات مجمّعة حسب الموديول (Checkboxes)، مع حماية أدوار النظام الأساسية من التعديل أو الحذف
- **Shell تنقل ديناميكي**: قائمة جانبية تُظهر فقط الموديولات التي يملك المستخدم صلاحية الوصول إليها، ومنطقة محتوى تتبدل حسب الموديول المختار
- إصلاح معماري مهم: تم توحيد دورة حياة (Scope) حقن الاعتماديات بحيث تُستخدم نفس الـ Scope طوال عمر التطبيق، لتفادي خطأ "Cannot resolve scoped service from root provider" عند الوصول لقاعدة البيانات من شاشات لاحقة بعد تسجيل الدخول

### Phase 2 — موديول المخزون (Inventory)
- **الأصناف (Items)**: بطاقة صنف كاملة — رمز، باركود، الاسم العلمي والتجاري، التركيز، الشكل الصيدلاني، الفئة، الوحدة، الشركة المصنّعة، أسعار افتراضية، نسبة الضريبة، حدود إعادة الطلب (Min/Max/Reorder Point)، علامتا "يتطلب وصفة طبية" و"مادة خاضعة للرقابة"
- **الدفعات وتتبع الصلاحية (Batches)**: كل دفعة مرتبطة برقم دفعة، تاريخ صلاحية، سعر شراء/بيع خاص بها، وكمية حالية — بحيث تختلف التكلفة الفعلية بين دفعة وأخرى لنفس الصنف
- **حركة المخزون (Stock Transactions)**: دفتر حركات كامل (Ledger) لكل تغيير في الكمية — استلام، تسوية (زيادة/نقصان)، إتلاف منتهي الصلاحية — مع رصيد بعد كل حركة، بحيث يمكن دائماً تتبّع "من أين جاء هذا الرقم"
- **استلام دفعة جديدة**: شاشة Receive Stock تُنشئ دفعة جديدة أو تزيد كمية دفعة موجودة، وتُسجّل حركة "استلام" تلقائياً
- **تسوية المخزون (Stock Adjustment)**: شاشة تسوية بسبب مذكور إلزامياً (جرد، تلف، خطأ إدخال، إلخ) تُسجّل حركة "تسوية" وتُحدّث رصيد الدفعة
- **نظرة عامة على المخزون**: تقرير حي لكل الأصناف حسب المخزن — الكمية الحالية، حالة "أقل من الحد الأدنى"، وتنبيهات الأصناف القريبة من الانتهاء أو المنتهية فعلياً (قابلة للتصفية بعدد أيام قبل الانتهاء)
- **تصنيفات ووحدات وشركات مصنّعة**: شاشة إدارة موحدة (Grid قابل للتحرير المباشر) لكل من الفئات والوحدات والشركات المصنّعة
- صلاحيات جديدة: `Inventory.ManageLookups`, `Inventory.ManageItems`, `Inventory.ReceiveStock`, `Inventory.AdjustStock`, `Inventory.ViewStock`
- بيانات أولية تلقائية (Seed): وحدة "قطعة" وفئة "عام" لتفادي شاشة أصناف فارغة عند أول تشغيل

### Phase 3 — الموردون والمشتريات (Purchasing)
- **الموردون**: بطاقة مورد كاملة (اسم، جهة اتصال، هاتف، عنوان، شروط الدفع)، تفعيل/تعطيل
- **أوامر الشراء (Purchase Orders)**: إنشاء أمر شراء بعدة أسطر أصناف، دورة حالة كاملة (مسودة → معتمد → مستلم جزئياً/كلياً → ملغى)، حذف مسموح فقط للمسودات
- **استلام البضاعة (Goods Receipt)**: يمكن إنشاؤه من الصفر أو من أمر شراء (تعبئة تلقائية للأسطر المتبقية غير المستلمة)، كل سطر يحدد رقم الدفعة وتاريخ الصلاحية وسعر الشراء الفعلي؛ عند "الترحيل" (Post) يتم استدعاء `IInventoryService.ReceiveBatchAsync` داخلياً لكل سطر — أي أن استلام البضاعة **لا يتلاعب بجداول المخزون مباشرة** بل يعيد استخدام نفس منطق موديول المخزون من Phase 2، مما يضمن اتساق دفتر حركة المخزون بالكامل
- **فواتير الشراء**: إنشاء فاتورة من الصفر أو بالتحميل التلقائي من مستند استلام مُرحّل (نفس المورد، نفس الأصناف والكميات والأسعار)، تسجيل دفعات جزئية أو كاملة مع تتبع "المبلغ المتبقي"، إلغاء الفاتورة
- كل عملية ترحيل (PO → GR → Invoice) مبنية على تحديث حالة تلقائي متسق عبر الكيانات المرتبطة
- صلاحيات جديدة: `Purchasing.ManageSuppliers`, `Purchasing.ManageOrders`, `Purchasing.ReceiveGoods`, `Purchasing.ManageInvoices`

### Phase 4 — المبيعات ونقطة البيع (Sales / POS)
- **شاشة نقطة البيع (POS)**: بحث سريع بالاسم أو الرمز أو الباركود (Enter للبحث، نقر مزدوج للإضافة للسلة — صديقة لقارئ الباركود)، سلة قابلة للتعديل (كمية، سعر، خصم لكل سطر)، اختيار عميل وطريقة دفع، خصم إضافي على الفاتورة، حساب تلقائي للضريبة والإجمالي والباقي عند الدفع نقداً
- **صرف المخزون تلقائياً بمنطق FEFO**: عند إتمام البيع، يستدعي موديول المبيعات داخلياً `IInventoryService.IssueStockFefoAsync` الذي يخصم من أقرب الدفعات انتهاءً أولاً (First-Expiry-First-Out) عبر دفعة واحدة أو أكثر عند الحاجة — موديول المبيعات لا يلمس جداول المخزون مباشرة أبداً، فيبقى دفتر حركة المخزون من Phase 2 هو المصدر الوحيد للحقيقة
- **العملاء**: بطاقة عميل كاملة (اسم، هاتف، عنوان)، تفعيل/تعطيل
- **فواتير المبيعات**: سجل كامل لكل عمليات البيع مع تفاصيل كل فاتورة
- **المرتجعات**: من داخل تفاصيل الفاتورة، إرجاع جزئي أو كامل لكل سطر على حدة مع سبب إلزامي؛ يستدعي داخلياً `IInventoryService.RestockBatchAsync` لإعادة الكمية إلى **نفس الدفعة** التي بيعت منها أصلاً (وليس دفعة عشوائية)، حفاظاً على دقة تتبع الدفعات
- **إلغاء فاتورة كاملة**: متاح فقط قبل أي عملية إرجاع منها، ويعيد كامل الكمية للمخزون تلقائياً
- صلاحيات جديدة: `Sales.ManageCustomers`, `Sales.UsePos`, `Sales.ViewInvoices`, `Sales.ProcessReturns`, `Sales.VoidInvoices`

### Phase 5 — الوصفات الطبية والتأمين الطبي (Prescriptions & Insurance)
- **الأطباء**: سجل بسيط (اسم، رقم ترخيص، اختصاص، هاتف) لتوثيق من وصف الدواء لأغراض التدقيق التنظيمي
- **الوصفات الطبية**: إنشاء وصفة لعميل محدد من طبيب محدد، بعدة أسطر أدوية (تظهر فقط الأصناف المعلّمة "يتطلب وصفة طبية")، مع كمية موصوفة وتعليمات جرعة لكل سطر
- **الصرف التدريجي**: الوصفة لا تُصرف دفعة واحدة بالضرورة — يمكن للعميل تعبئتها عبر أكثر من زيارة؛ كل عملية بيع تُحدّث `QuantityDispensed` لكل سطر تلقائياً وتُحدّث حالة الوصفة (نشطة → مصروفة جزئياً → مصروفة بالكامل)
- **تكامل صارم مع نقطة البيع**: `CheckoutAsync` في موديول المبيعات (Phase 4) يرفض أي عملية بيع تحتوي على صنف يتطلب وصفة طبية بدون ربطها بوصفة نشطة تعود لنفس العميل وتحتوي على ذلك الصنف بكمية كافية — هذا التحقق يقع في نقطة الاختناق الوحيدة (Checkout) وليس فقط بالواجهة، فلا يمكن تجاوزه
- **تراجع تلقائي متسق**: إلغاء فاتورة أو إرجاع جزء منها يُعيد الكمية المصروفة تلقائياً لسطر الوصفة المرتبط ويُصحح حالتها، فتبقى قابلة للصرف مجدداً
- **شركات التأمين وبوليصات التأمين**: ربط عميل بشركة تأمين تحت رقم بوليصة ونسبة تغطية محددة، ضمن مدى زمني (تاريخ بداية/انتهاء)
- **مطالبات التأمين**: عملية مطالبة استرداد بعدية (Back-office) على فاتورة مبيعات مكتملة بالفعل — العميل يدفع كامل المبلغ أو الجزء غير المغطى عند البيع، ثم تُقدَّم المطالبة لاحقاً لشركة التأمين بدورة حياة كاملة (مُقدَّمة → قيد المراجعة → معتمدة/مرفوضة → مدفوعة)، مع حماية تمنع تجاوز المبلغ المعتمد للمبلغ المطالب به، وتجاوز المطالب به لإجمالي الفاتورة
- صلاحيات جديدة: `Prescriptions.Manage`, `Insurance.ManageCompanies`, `Insurance.ManagePolicies`, `Insurance.ManageClaims`

### Phase 6 — المحاسبة المالية (Accounting)
- **دليل الحسابات (Chart of Accounts)**: شجرة حسابات هرمية (أصول، خصوم، حقوق ملكية، إيرادات، مصاريف) مع حسابات نظام أساسية (نقدية، مخزون، ذمم مدينة/دائنة، ضريبة مستحقة/مدخلات، إيرادات مبيعات) تُنشأ تلقائياً عند أول تشغيل ولا يمكن حذفها أو تعديل رموزها لأن الترحيل التلقائي يعتمد عليها بالاسم
- **القيود اليومية (Journal Entries)**: كل قيد يخضع لتحقق صارم قبل الترحيل — سطرين على الأقل، كل سطر مدين أو دائن (وليس كليهما)، وتطابق إجمالي المدين مع إجمالي الدائن قبل السماح بالحفظ؛ القيود اليدوية والتلقائية تُرحَّل فوراً (Posted) ولا رجوع عنها
- **الترحيل التلقائي**: موديولات المبيعات والمشتريات والتأمين **لا تكتب أي قيد محاسبي بنفسها إطلاقاً** — كل واحدة تستدعي `IAccountingService` عند حدوث الحدث المالي فعلياً:
  - فاتورة بيع مكتملة → مدين نقدية / دائن إيرادات مبيعات + دائن ضريبة مستحقة
  - فاتورة شراء مستلمة → مدين مخزون + مدين ضريبة مدخلات / دائن ذمم دائنة
  - دفعة على فاتورة شراء → مدين ذمم دائنة / دائن نقدية أو بنك
  - دفعة مطالبة تأمين معتمدة → قيد تحصيل مقابل حساب التأمين
- **الصناديق النقدية والحسابات البنكية**: سجل بسيط لكل مصدر نقدي فعلي (صندوق POS، حساب بنكي)، تُستخدم كخيار "المصدر" في شاشات المصاريف والسندات
- **فئات المصاريف والمصاريف**: تسجيل مصروف فعلي (إيجار، فواتير، لوازم) مرتبط بفئة وحساب دفع (صندوق أو بنك)، يُرحَّل تلقائياً كقيد محاسبي
- **سندات القبض والصرف العامة**: لحركات النقد اليدوية التي لا تصدر عن موديول آخر تلقائياً (رأس مال المالك، استرداد متنوع، سحب نقدي) — منفصلة تماماً عن الدفعات التلقائية لفواتير الشراء ومطالبات التأمين
- صلاحيات جديدة: `Accounting.ManageChartOfAccounts`, `Accounting.ManageJournalEntries`, `Accounting.ManageCashAndBank`, `Accounting.ManageExpenses`, `Accounting.ManageReceiptsPayments`
- بيانات أولية تلقائية (Seed): شجرة حسابات نظام كاملة + صندوق نقدي رئيسي واحد على الفرع الرئيسي

### Phase 7 — التقارير ولوحة التحكم (Reports & Dashboard)
- **لوحة التحكم الرئيسية**: تُعرض مباشرة بعد تسجيل الدخول (أصبحت الشاشة الافتراضية للـ Shell بدلاً من شاشة ترحيب فارغة) — مؤشرات حيّة لليوم الحالي: مبيعات، عدد فواتير، ربح إجمالي، مصاريف، صافي المركز النقدي، بالإضافة لتنبيهات فورية (أصناف أقل من الحد الأدنى، دفعات قاربت على الانتهاء، دفعات منتهية فعلياً) وجدول لأكثر الأصناف مبيعاً اليوم
- **ملخص المبيعات**: تقرير بمدى تاريخي وفرع اختياري — إجمالي الفواتير، المبيعات قبل/بعد الضريبة، الخصومات، وتوزيع المبالغ حسب طريقة الدفع
- **تقرير حركة المخزون**: سجل كامل لكل حركة مخزون (استلام/بيع/إرجاع/تسوية/إتلاف) ضمن مدى تاريخي، قابل للتصفية حسب الفرع والصنف، مع الرصيد بعد كل حركة
- **ميزان المراجعة (Trial Balance)**: كل حساب برصيده المدين/الدائن كما في تاريخ محدد، مبني مباشرة من دفتر القيود المُرحّلة فقط
- **قائمة الدخل (Income Statement)**: الإيرادات والمصاريف ضمن مدى تاريخي لحساب صافي الربح
- **التصدير والطباعة بدون أي تبعية خارجية**: "تصدير Excel" هو تصدير CSV بترميز UTF-8 مع BOM (يفتح مباشرة في Excel ويعرض العربية بشكل صحيح دون الحاجة لمكتبة Office أو مكتبة جداول بيانات طرف ثالث)؛ و"تصدير PDF" يتم عبر نافذة الطباعة القياسية في ويندوز باختيار طابعة "Microsoft Print to PDF" الافتراضية — دون أي مكتبة PDF خارجية
- صلاحيتان جديدتان: `Dashboard.View` (لوحة التحكم فقط) و `Reports.View` (كل شاشات التقارير الأربع)

### Phase 8 — الموارد البشرية والرواتب (HR & Payroll)
- **الموظفون**: بطاقة موظف كاملة (رمز، رقم وطني، هاتف، عنوان، مسمى وظيفي، فرع، وردية اختيارية، راتب أساسي شهري)، مع إمكانية ربط الموظف بحساب دخول للنظام (User) لتمكين تسجيل حضوره الذاتي
- **الورديات**: تعريف أوقات دوام (بداية/نهاية) تُسند للموظفين
- **الحضور والانصراف**: تسجيل دخول/خروج سريع لموظف مُحدد، بالإضافة لتسجيل يدوي/تصحيحي لأي حالة حضور (حاضر، غائب، إجازة، غياب بعذر) مع فلترة حسب المدى الزمني والموظف
- **عمولات الموظفين**: تسجيل عمولة فعلية لموظف (قد ترتبط بفاتورة بيع محددة أو تكون عمولة عامة)
- **دورات الرواتب**: تُحسب تلقائياً لكل موظف نشط في الفرع المحدد — الراتب الأساسي + كل العمولات غير المدفوعة ضمن فترة الدورة (وتُربط هذه العمولات بسطر الراتب فور توليد الدورة، لمنع احتسابها مرتين في دورة لاحقة)
- **دورة حياة الراتب**: مسودة (تعديل الاستقطاعات لكل موظف حسب السبب) → اعتماد (لا تعديل بعده) → صرف — وعند الصرف فقط تُسجَّل عمولات الموظفين كمدفوعة، ويُرحَّل القيد المحاسبي عبر `IAccountingService.PostPayrollPaymentAsync` — بنفس مبدأ "لا ترحيل إلا لحظة خروج المال فعلياً" المتبع في كل موديولات النظام الأخرى
- صلاحيات جديدة: `Hr.ManageEmployees`, `Hr.ManageAttendance`, `Hr.ManageCommissions`, `Hr.ManagePayroll`

### Phase 9 — التشغيل النهائي (Auto-Update, Backup/Restore, Licensing)
- **نظام التحديث التلقائي**: يتحقق من ملف JSON صغير منشور على `api.alliba.uk` (نفس بنية التحديث المستخدمة في مشاريعك السابقة)، يقارن الإصدار الحالي بأحدث إصدار منشور، وعند توفر تحديث يقوم بتنزيله مع شريط تقدم ثم تشغيله بصمت (`/S`، متوافق مع مخرجات Advanced Installer)، ثم يُنهي التطبيق الحالي ليحل المثبّت محل الملفات. فشل الشبكة لا يمنع فتح التطبيق أبداً — يُعامل كـ"لا يوجد تحديث". زر "التحقق من التحديثات" متاح دائماً بأعلى الشاشة الرئيسية.
- **النسخ الاحتياطي والاستعادة**: يستخدم أوامر SQL Server الأصلية (`BACKUP DATABASE` / `RESTORE DATABASE`) مباشرة بدل أي صيغة تخزين مخصصة — فملفات `.bak` الناتجة قابلة للاستعادة بأي أداة SQL Server قياسية (SSMS مثلاً) حتى بدون هذا التطبيق، وهو ما يهم فعلياً عند التعافي من كارثة. الاستعادة تُحوّل قاعدة البيانات إلى `SINGLE_USER WITH ROLLBACK IMMEDIATE` (تُغلق كل الاتصالات المفتوحة بما فيها اتصال التطبيق نفسه) ثم تُعيدها لـ `MULTI_USER` — مع تحذير صريح وقوي بالواجهة قبل التنفيذ.
- **نظام الترخيص التجاري**: ترخيص offline بالكامل — لا يتصل التطبيق بأي خادم ترخيص. ملف الترخيص (`.lic`) عبارة عن JSON موقّع بتوقيع HMAC-SHA256 بمفتاح يُقرأ من متغير البيئة PHARMACYERP_LICENSE_SIGNING_SECRET، مرتبط ببصمة الجهاز (اسم الجهاز + معرّف محلي دائم). **تم توثيق الحد الأمني بوضوح بالكود**: هذا مستوى حماية قياسي لتراخيص سطح المكتب دون اتصال، وليس ادعاءً بمناعة كاملة ضد التعديل.
  - **إنفاذ فعلي حقيقي وليس شكلياً**: تم ربط `ILicenseService` مباشرة داخل `BranchService.CreateAsync` و `UserService.CreateAsync` — إنشاء فرع أو مستخدم جديد يتحقق فعلياً من عدم تجاوز `MaxBranches` / `MaxUsers` المحددة بالترخيص الحالي قبل السماح بالعملية
  - **أداة داخلية منفصلة للجهة المرخِّصة**: مشروع Console صغير `tools/LicenseIssuer` (غير مرفق مع أي نسخة تُباع للعميل) يستقبل اسم العميل وبصمة جهازه وعدد الفروع/المستخدمين المسموح بهم ومدة الصلاحية، ويصدر ملف `.lic` موقّعاً جاهزاً للإرسال للعميل
  - شاشة "الترخيص" بالتطبيق تعرض الحالة الحالية (صالح/منتهي/غير متطابق مع الجهاز)، بصمة الجهاز (قابلة للنسخ لإرسالها للجهة المرخِّصة)، وزر استيراد ملف الترخيص
- صلاحيتان جديدتان: `System.ManageBackup`, `System.ManageLicense`

**⚠️ قبل الإطلاق التجاري الفعلي**: اضبط `PHARMACYERP_LICENSE_SIGNING_SECRET` بمفتاح سري فريد ومتطابق للتطبيق وأداة الإصدار، ولا تُرفق مشروع `LicenseIssuer` أبداً مع أي نسخة تُسلَّم أو تُباع لعميل — إنه أداة
داخلية للجهة المرخِّصة فقط.

### Phase 10 — الاختبارات الآلية (Automated Test Suite)
مشروعان للاختبار مبنيان على xUnit + FluentAssertions، وهما آخر بند كان محجوزاً بخارطة الطريق الأصلية:

**`tests/PharmacyERP.Domain.Tests`** — اختبارات وحدة خالصة بلا أي تبعية على قاعدة بيانات:
- `UserTests` — منطق `IsLockedOut()` الذي يحمي شاشة الدخول
- `PrescriptionItemTests` — حساب `QuantityRemaining` (بما فيه ألا يعطي رقماً سالباً أبداً عند الصرف الزائد)
- `InsurancePolicyTests` — صلاحية البوليصة `IsCurrentlyValid()` بكل حالاتها الحدية
- `BatchTests` — `IsExpired()` و `DaysUntilExpiry()`، مع تثبيت الحالة الحدية الأهم: **الدفعة المنتهية "اليوم" تبقى قابلة للصرف** (خطأ بمقدار يوم واحد هنا يعني إما منع مخزون سليم أو بيع مخزون منتهي)

**`tests/PharmacyERP.Application.Tests`** — اختبارات تكامل للخدمات فوق مزوّد EF Core InMemory، مع الـ Audit Interceptor الحقيقي مرفقاً:
- `InventoryServiceFefoTests` — **الأهم في المجموعة**: تثبّت ترتيب السحب FEFO فعلياً (الدفعات تُدخل بترتيب معاكس مقصود حتى يفشل أي تنفيذ ساذج يسحب بترتيب الإدخال)، السحب المتعدد الدفعات، أن **الفشل ذرّي بلا خصم جزئي**، أن كل دفعة تُنتج حركة مخزون واحدة، وأن الإرجاع يعود لنفس الدفعة الأصلية
- `AccountingServiceJournalTests` — رفض القيد غير المتوازن، رفض سطر يحمل مديناً ودائناً معاً (حتى لو تطابقت الإجماليات)، رفض القيد بسطر واحد، وأن الرفض لا يحفظ أي شيء
- `AuthServiceLockoutTests` — القفل عند المحاولة الخامسة بالضبط وليس الرابعة، رفض كلمة المرور **الصحيحة** أثناء نافذة القفل، عودة الدخول بعد انقضاء الـ15 دقيقة، وتصفير العدّاد بعد نجاح الدخول (عدّاد عالق يقفل مستخدماً بريئاً لاحقاً)
- `LicenseEnforcementTests` — إثبات أن حدود الترخيص **مُنفَّذة فعلاً في منطق العمل** وليست شاشة زخرفية: نفس العملية تنجح مع ترخيص متاح وتُرفض مع ترخيص مستهلك

#### ما تم التحقق منه فعلياً وما لم يُتحقق منه
- ✅ **مشروع `PharmacyERP.Domain` جُمِّع فعلياً بنجاح** (0 أخطاء، 0 تحذيرات) — كل الكيانات والـ enums سليمة نحوياً ودلالياً
- ✅ **كل ثوابت الـ Domain نُفِّذت فعلياً وتم التحقق منها** (19 تحقق: `IsLockedOut`, `QuantityRemaining`, `IsCurrentlyValid`, `IsExpired`, `DaysUntilExpiry`) — نجحت كلها
- ⚠️ **اختبارات الخدمات مكتوبة لكنها لم تُنفَّذ بعد**: بيئة التطوير التي أُنشئ فيها المشروع لا تصل إلى `nuget.org`، فتعذّر تنزيل حزم xUnit / EF Core InMemory وتشغيل `dotnet test`. **الرجاء تشغيل `dotnet test` على جهازك** (بعد إتاحة الإنترنت لـ NuGet) قبل الاعتماد عليها؛ من المتوقع أن تحتاج بعض الاختبارات تعديلات طفيفة عند أول تشغيل، خصوصاً بسبب أن مزوّد InMemory لا يدعم `IsRowVersion()` بشكل كامل — إن ظهر خطأ متعلق بـ `RowVersion` فالحل المعتاد هو تعطيل الـ concurrency token على مستوى موديل الاختبار فقط.

#### إصلاح إضافي في هذه المرحلة
- **`NuGet.config`**: كان يحتوي على رابط feed وهمي لـ DevExpress (`YOUR_FEED_KEY`)، وهذا كان يُفشل `dotnet restore` **لكل** مشاريع الحل بأخطاء NU1301 مُبهمة — حتى المشاريع التي لا تعتمد على DevExpress إطلاقاً. تم تعطيل السطر مع تعليق يشرح كيفية تفعيله، فأصبح الحل يُستعاد جاهزاً من أول مرة.

## قبل أول تشغيل
1. تأكد من نسخة SQL Server المحلية أو السيرفر، وعدّل `ConnectionStrings:DefaultConnection` في
   `src/PharmacyERP.WPF/appsettings.json` حسب بيئتك.
2. افتح Package Manager Console، اختر `PharmacyERP.Infrastructure` كـ Default Project، ثم نفّذ:
   ```
   Add-Migration InitialCreate -StartupProject PharmacyERP.WPF -Context ApplicationDbContext
   ```
   (التطبيق سينفّذ `Database.MigrateAsync()` تلقائياً عند أول تشغيل، فلا حاجة لـ Update-Database يدوياً.)
3. تأكد من توفر ترخيص DevExpress WPF صالح على جهاز التطوير (الحزم مرجعّة بصيغة `24.1.*` في
   `PharmacyERP.WPF.csproj` وتحتاج NuGet feed خاص بـ DevExpress). ملاحظة: الشاشات الحالية تستخدم
   عناصر WPF القياسية (DataGrid وغيرها) للحفاظ على الاستقرار؛ سيتم استبدالها بعناصر DevExpress
   المتقدمة في جولة تحسين UI/UX القادمة.
4. **مهم قبل أي بيع فعلي**: افتح `src/PharmacyERP.Infrastructure/Services/LicenseService.cs`
   و`tools/LicenseIssuer/Program.cs` واضبط متغير البيئة `PHARMACYERP_LICENSE_SIGNING_SECRET` بالمفتاح السري نفسه لكليهما. بدون ترخيص مفعَّل، إنشاء فروع أو
   مستخدمين إضافيين (بعد الفرع/المستخدم الافتراضيين اللذين ينشئهما الـ Seeder) سيُرفض تلقائياً —
   استخدم أداة `LicenseIssuer` لإصدار أول ملف `.lic` لجهاز التطوير الخاص بك من شاشة "الترخيص"
   بالتطبيق (انسخ بصمة الجهاز المعروضة هناك وأدخلها في الأداة).
5. شغّل المشروع (F5) من `PharmacyERP.WPF`.

## إعدادات خاصة لا تُرفع إلى Git
- اضبط `PHARMACYERP_INITIAL_ADMIN_PASSWORD` قبل إنشاء أول مدير.
- اضبط `PHARMACYERP_LICENSE_SIGNING_SECRET` بالمفتاح نفسه في التطبيق وأداة الإصدار؛ لا يوجد مفتاح مضمّن.
- اضبط `ConnectionStrings__DefaultConnection` لاتصال SQL Server عبر متغير بيئة؛ الإعداد المنشور فارغ.
- تطبيق WPF يحتاج Windows؛ يمكن بناء المكتبات وتشغيل اختبارات Domain وApplication على Linux.

## نتائج التحقق في البيئة السحابية
- SDK: .NET 8.0.425، وبناء WPF باستخدام `-p:EnableWindowsTargeting=true` ناجح (تحذيرات CS1998).
- Domain: 21 اختبارًا ناجحًا. Application: 17 ناجحًا و2 فاشلان.
- فشل اختبار حد الفروع لأن فحص الترخيص معلّق في BranchService؛ وفشل اختبار القفل لأن IsLockedOut يستخدم ساعة النظام بدل ساعة الاختبار المحقونة. لم تُغيّر هذه الوظائف أثناء استيراد المشروع.
- تشغيل واجهة WPF والتحقق من SQL Server يحتاجان Windows وإعدادات اتصال محلية.
